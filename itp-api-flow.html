Interpersonal Transaction Protocol · API v1 · ITP schema 0.2

How an interaction runs through the ITP API

A JavaScript application runs an interaction between two agents, each of which is either a human participant or a formal model. The server owns the interaction: it decides whose turn it is, runs the model agents, validates every state vector, and hands each client the experience its partner produced.

This maps that to the endpoints, the modules, and the rules they keep. The in-process flow between two formal models is the companion document, itp-communication-flow.html.

02 Interaction states

The server is the authority on the state and the turn number. An interaction with two formal model agents needs no registration and runs to completion inside the creation request; one with a human agent waits until every human has registered.

waitingForRegistration Created. One or more human agents have not registered yet.
→
running Turn 1 onward. activeAgentIds names who must act.
→
completed numberOfTurns reached. The normal ending.
terminated A client called /end before the last turn.
failed A model raised, or produced a vector outside its own state space.

The specification also defines ready and expired. Interactions move from waitingForRegistration straight to running, which the specification permits, and nothing expires an interaction yet — there is no reaper and no interaction lifetime.

numberOfTurnsReached — the interaction played every turn it was created with.
terminatedByClient — a client called POST /end.
modelFailure — a formal model raised, or left its own state space.
serverError — a converted vector left the target state space.
participantDisconnected · registrationTimeout · interactionExpired — defined, not yet raised.

03 The turn engine

Interactions are alternating: one turn is one action slot with exactly one acting agent, which is what activeAgentIds and the results representation describe. numberOfTurns therefore counts single actions, not exchanges — a four-turn interaction is four behaviors, two from each agent.

06 What crosses the wire, and what is kept

The client sends and receives bare state vectors. The ITP message is built on the server, so the browser never assembles source_agent, target_agent or a timecode — and the interaction still produces the same record as one driven by the local runner.

On the wire

What a client posts, and what it reads back. The vector is validated against the model's stateSpaceSchema in both directions.

// POST .../agents/{agentId}/actions
{
  actionId: "client-action-1",
  turn: 1,
  behavior: { Theta: 90.0, R: 0.6 }
}
// GET .../agents/{agentId}/perception
{

  sessionStatus: "running",
  perceptionId: "d87a225a-…",
  cursor: "3",
  turn: 3,
  actionRequired: true,

               R: 0.4172976538233931 },
  sourceAgentId: "9b579baa-…"
}

Kept on the server

The ITP message the action above became, stored in the interaction's Communication and returned by /results under itpMessages.

{
  schema_version: "0.2",
  source_agent: { id: "ec554a99-…", state_space: "ipc",
                analysis_unit: "monadic" },
  target_agent: { id: "9b579baa-…", state_space: "ipc",
                analysis_unit: "monadic" },
  timecode: { timestamp: "1:01", interaction_turn: 1,

  context: "workplace_colleague_conversation",
  metadata: { session_id, agent_role: "A",
            agent_type: "human" }
}

One API turn maps onto the ITP timecode as interaction_turn = (turn + 1) // 2 and message_index = 2 - (turn % 2), so API turns 1 and 2 are the two messages of ITP interaction turn 1.

07 Tokens and invitation codes

Every interaction issues its own tokens, and a code exists only when a second human participant has to join from another browser.

One token per client, bound to an agent

Creating an interaction issues a token; joining issues a second one. Both are stored as SHA-256 hashes against a session id.

A token becomes bound to the agent it registers. A bound token may poll and act only for its own agent — addressing the other is 403. Reading status and ending the interaction stay open to either client.

The six-digit code

Generated with secrets, unique among active invitations, bound to one interaction and one agent, single use, expiring after 30 minutes, and stored only as a hash.

It is disclosed exactly once, in the creation response. GET /interactions/{id} returns its status but never the code again.

Why the join endpoint is rate-limited

Six digits is a million possibilities, which is not many. Failed attempts are counted in a 60-second window per source address, per client id, per code, and overall, and a client over the limit gets 429 with retryAfterSeconds.

clientRequestId is scoped

The creation response carries a token, so replaying it to anyone who repeats the identifier would hand out another client's access. A replay must match the exact payload and the source address; anything else is 409.

08 Rules the API keeps

The server owns the turn

Clients never decide whose turn it is. They read turn from a perception and send it back; a mismatch is 409. Each agent submits at most one behavior per turn.

Every vector is validated, both ways

Submitted behaviors and returned experiences are checked against the same compiled stateSpaceSchema, geometry included. A model that leaves its own state space fails the interaction rather than emitting an invalid state.

Model agents are the server's to run

They are registered and executed internally, never driven by a client. Submitting a behavior for one is 403.

Polling is safe to repeat

A GET never consumes a perception. The same request returns the same perception until the client advances its cursor, so a dropped response costs nothing.

Actions are idempotent, per agent

actionId is scoped to the agent that sent it, so two clients using counter-style ids do not collide. A retry with the same content returns the original response; different content is 409.

The ITP record survives

Every behavior becomes an ITP message in the interaction's Communication, original and converted. With persistence enabled, /results returns both the turn record and those messages.
