## What this is

Code repository of the **ITP framework**: the Interpersonal Transaction Protocol (a standardized numerical message format letting formal models of interpersonal interaction communicate), the ITP platform (the API that hosts models and runs interactions), and the ITP interfaces (client applications such as PerTRAIN). Work in progress; do not call it a reference implementation in public text. `README.md` is the public overview, written for readers of the paper; `docs/development.md` holds the layout, design decisions, ports, tests and planned work, `docs/deployment.md` the deployed API and the release steps, `docs/api_design.md` the API design and its known gaps. Put maintainer detail in `docs/`, not in the README. PerTRAIN (`ITPGenerator` in `personalization-backend`) is the only interface (client application) connected so far; connecting MovES is planned. The README follows the paper's structure: the ITP, the ITP platform, the ITP interfaces. Interactions between two humans work in the API but are untested with participants and left out of the paper; the README lists them as planned. The README's *How to contribute* (API key by GitHub issue, platform stores only ITP messages and the interaction description, never a paradigm's text) is the public policy; keep it in step with how keys are actually issued.

## Architecture

Three layers, deliberately decoupled:

1. **Formal models** (`src/formalmodels/`) — produce and integrate numerical ITP values. `BaseFormalModel` is the abstract base; `DummyFormalModels.py` holds `DummyIPCFormalModel` / `DummySASBFormalModel`; `LASSIFormalModel.py` is the agency-communion (`ac`) model, a reimplementation of the reference in the `lassi_simulations` repository (`handoff/formal-model-spec.md` there). One exchange moves the mean of a per-axis state distribution to a convex mixture of the previous mean (`mu_prev`), the behavioral default (`BD`) and the partner-implied target (`partner_target`), then makes the distribution the agent's `repertoire` exponentially tilted onto that mean: the realised mean equals `mu_t` exactly, and clipping is structurally impossible — a clip in this model hides a broken invariant. The spec's notation and this module's names differ; the mapping is in the module docstring. Reactivity `IR` is **signed** in `[-1, +1]`: magnitude is the weight on the partner, sign is the response direction. `m` (`complementarity_direction`) belongs to the axis, not the person. Its per-axis parameters live in `configs/formal_model_parameters.yaml` and are stated on the **ITP 1-based scale** `1 … N`, matching `lassi_simulations`; the internal grid is symmetric and zero-centred, and conversion happens in `to_itp_state` / `to_internal_state`. `step_record()` exposes every intermediate of the last update, under the field names the handoff vectors use, for the visualization and the conformance test. `lassi_parameter_space()` publishes what an agent may choose (BD strictly inside 1 to 7, IR in [-1, 1], per axis; the config values are the defaults, everything else stays fixed) and `lassi_parameters_with` merges a choice into the config; the generic part is `ParameterSpace.py`.
2. **ITP messages** — nested dicts: `source_agent`/`target_agent` = `{id, state_space, analysis_unit}`, `values` = `{state_space, analysis_unit, data}`, plus `schema_version`, `timecode`, `context`, optional `metadata`. Spec/validation lives in `src/ITPSpecification.py` (`schema_version = "0.2"`).
3. **Communication sessions** (`src/communication/Communication.py`) — a stateful ITP message session that stores and validates messages (original and converted). It does **not** hold model objects, clients, or users.

Cross-state-space delivery: whoever delivers a message converts its `values` to the target's state space first, using `src/converter/` (`BaseConverter`, `ConverterRegistry`, `BehavioralStateSpaceConverters`) — the **runner** locally, `APISpecification` for messages crossing the API. Converters live outside `Communication`. They do not enforce geometry constraints in general; the API validates every converted vector against the target state space and fails the interaction if one leaves it. A client registers in the space its own scale speaks: the PerTRAIN backend (`ITPGenerator` in `personalization-backend`) registers as `ac`, because its axes have seven states. A client with another number of states needs a new state space under its own identifier (IBSSS file, `STATE_SPACE_SOURCES` entry, converters, redeploy), never a change to `ac`, whose range is tied to LASSI; the steps are in `docs/development.md` under *Converters and new state spaces*. The IPC neutral center is settled: the circumplex **includes** it, marked by `R = 0`, where `Theta` is undefined and reported as `NEUTRAL_CENTER_ANGLE` — never interpret `Theta` unless `R > 0`.

**Visualization** (`src/visualization/`) — Dash dashboards, decoupled from the models. `BaseVisualizer` owns the shared style, page scaffolding and Dash hosting; subclasses implement `validate_source` / `build_body` / `register_callbacks`. `FormalModelVisualizer` takes a formal model, `InteractionVisualizer` takes ITP messages (trajectory dashboard not implemented yet), `LASSIFormalModelVisualizer` is the LASSI update walk-through (mean rule, response direction, tilt, repeated exchanges). Dashboards recompute on throwaway objects and never mutate the model they render. Style is the PerTRAIN design system, defined once as class attributes on `BaseVisualizer` (light neutrals, `#2C6BB5` primary, system sans, no font binaries) — take colours from there rather than writing a hex into a figure. `AGENCY = #315A7D` and `COMMUNION = #B84650` are the agreed pair for agency-communion figures and are reserved for the axes: the current state of an axis is drawn in its axis colour, everything else keeps a role colour that does not change with the axis. The two flow diagrams at the repo root use the same palette as CSS variables.

**Interaction report and paper figures** — `src/run_interaction_report.py` writes a self-contained HTML page (one file, no dependencies, nothing fetched) from a results folder alone. `InteractionRecord` reads `interaction.json` and the message files and pairs each behavior as sent with its converted copy; steps are the API turn (`timecode.api_turn`, one message each), not `interaction_turn`, which counts exchanges. `InteractionReport` fills `src/visualization/templates/interaction_report.html` (placeholder `/*__ITP_REPORT_DATA__*/null`, exactly once). The page draws one SVG from independent panel functions (dialogue, one plane per agent in its own space with the partner's behavior as delivered, each dimension over turns) and exports it as SVG or PNG at the selected turn, so a paper figure is a frame of the supplement. Planes put communion right and agency up in both cartesian and polar spaces (`describe_state_space`). Agents are blue (`PRIMARY`) and amber (`CROSS`); the agency and communion colours stay on the axes. Paradigm text (e.g., PerTRAIN chats) is never on the platform: it comes as a CSV `turn,role,text` and is refused, not shown, when a row names a turn the record lacks or the wrong agent. Angles are not drawn across 0/360 and are left out at `R = 0`. A label's white halo is a separate `<text>` element under it (`text()` builds it from `paint-order: stroke`), never `paint-order` in the export: Word ignores `paint-order`, paints the stroke over the fill and loses the label in its own halo, which also cuts gaps into the circumplex. `examples/interaction-report/` holds the run behind Figure 2 and its written report: PerTRAIN dialog `3266e74a` (bar conflict over a joke, eight messages, gpt-4.1, local stack and local ITP server); `record/` is Lukas's record (Daniel's assessed text as human A in `ac`, the dummy IPC model as B), the one the figure shows at turn 8 in landscape; `lassi_record/` is Daniel's (LASSI with A: BD 5.5, IR −0.6; C: BD 3, IR 0.7, no conversion); `dialogue.csv` and `lassi_dialogue.csv` came from `pertrain_dialogue.py`. `dialog2/` and `dialog3/` hold the other two dialogs of that run (Daniel's LASSI with BD 3.5/IR 0.8 and 5/0.8, and a random draw), each with both records, both dialogue files and both reports; they are Figures E4 to E7 and Tables E1 to E3 of the ESM. In every legend the partner's side is labelled "assessed messages", because its points are the partner's text as the agent's own assessor rated it, not the states the partner's model set. Figure 1 is section 00 of `itp-api-flow.html`, a hand-written SVG with literal colours and fonts so the export renders the same in Word, with the same export buttons. Figures are laid out at 200 units per inch of print width, so 21 units are 7.5 pt at any width: Figure 1 is fixed at 6.2 in (1240 units); the report takes `--print-width` (`portrait` 6.2 in, `landscape` 9 in, or inches), and its dialogue column takes the share of the width closest to 40% (within 30 to 55%) at which the charts over turns, stretched to end level with it, stay between `DIMENSIONS_H` and `DIMENSIONS_MAX_H`, so both columns end on one line; it holds at most 1300 units (6.5 in) of height. Panels carry lettered heads, a) to d) in the order shown (dialogue, state spaces, trajectories over turns, legend); the trajectories head does not name the space, which the y axes and the --time-space choice carry. The header names each model agent's parameters when the record has them. Dialogue cards and plane titles name an agent by the part of its label before the first comma or bracket; the full labels sit in the legend block under the charts over turns. A PerTRAIN agent's record (partner's assessed text as human A in `ac`, the steering model as B, `clientRequestId` = PerTRAIN session) gets its dialogue from `examples/interaction-report/pertrain_dialogue.py`, which reads the local stack's database: A's k-th turn is the k-th partner message, B's k-th the agent's next own message. Such a record holds one model; a dialog of two model-steered agents leaves two records. `InteractionVisualizer.trajectories()` mixes original and converted messages; anything new should read through `InteractionRecord`.

**API** (`src/API/`) — implements `docs/ITP_API_Specification.pdf` under `/api/v1`: model catalogue, interaction lifecycle, server-authoritative alternating turns, participant registration, six-digit invitation codes, perception polling, idempotent action submission, RFC 9457 errors. `APISpecification` is routing/auth/errors only; `Interaction` owns the turn engine, `InteractionRegistry` owns tokens/invitations/idempotency (tokens are bound to the agent they registered; a bound token may only address its own agent), `ModelCatalogue` the model entries, `StateSpaceSchema` compiles IBSSS descriptions into validating JSON Schemas (plus geometry checks JSON Schema cannot express). The wire format is bare `experience`/`behavior` vectors; ITP messages are built server-side and stored in `Communication`. The two agents may run different models: `agents.X.modelId` overrides the top-level `modelId` for a model agent, every agent reports the model it runs as `model` (null for a human), and a pair whose state spaces no single converter connects is refused at creation (converters are not chained). Model parameters per agent go through the specification's `agents.X.configuration`: `parameterSelection` (`default` or `random`, a uniform draw rounded to two decimals), `randomSeed` (drawn and reported if missing), and `parameters` keyed by group then name, which win. `ModelEntry.parameter_space` declares what a model offers (`parameterSpace` in `GET /models/{id}`), `resolve_configuration` turns a configuration into values before the factory runs (factories take `(agent_id, parameters)`), and anything outside the space, or any configuration on a human or a model without a space, is a 422. Every model agent with a space reports `parameters` (`selection`, `randomSeed`, `explicit`, `values`) in its responses and in `interaction.json`, which also keeps the `clientRequestId`. Actions may leave out `turn` (the server takes the current one) and return the `cursor` to poll after for their answer; a repeated `clientRequestId` returns the interaction as it is now, so a client that lost its state recovers session and token. Interactions and tokens live in memory only; after a restart a request for an unknown interaction gets a 404 that says so, which is the client's cue to start a new one. Resuming interactions after a restart instead is described with its costs in `docs/api_design.md` under *Server restarts*. See `docs/api_design.md` for extensions to the spec and known gaps.

**Mock client** (`ui/index.html`, served by `src/run_mock_ui.py`) — stands in for the JavaScript application: catalogue, interaction creation, registration, invitation codes, long-polled perceptions, behavior inputs built from the model's `stateSpaceSchema`, and a log of every request and response. Each step is a collapsible card, auto-collapsing behind the current one. Plain HTML and JS, one file, no build step and no dependencies — keep it that way, and keep the palette on the PerTRAIN design system (neutral surfaces, `#2C6BB5` for actions, system sans, no font binaries). It is served on a port the API's CORS list allows — 5173 first, then the rest of 5173-5182 if that is taken; serving it from the API process would make it same-origin and hide that check. It learns which port the API bound from `mock-ui-config.json`, which `run_mock_ui` answers from memory. An API key field sends `X-API-Key` for the deployed API behind the gateway; the key stays in the field and never enters the request log. The catalogue card only lists models; the setup card has one model field per agent (offering available models only), plus, with two humans, the model the interaction is bound to. A model agent whose model publishes a `parameterSpace` gets a parameter box in the setup card (defaults, random with optional seed, or values by hand), and the status shows the values used. The interaction context is deliberately not a control there: it modulates nothing in any model yet. It is due to leave this repo and become the client participants use to let their own formal model exchange numbers with others (`docs/client_split.md`); until then, add nothing that makes it depend on `src/` or on sharing this checkout.

**Example web client** (`examples/itp-api-basic-web-client/`, by Stefan) — a participant-facing client for one paradigm: LASSI as agent A against a human in `ipc` as agent B, ten turns, model first, persistence off. Plain HTML and JS plus a PHP adapter (`public/api.php`) that holds the API key and the interaction token server-side and forwards to the API with `X-API-Key`. It accepts `https://` base URLs only, so it runs against the deployed API, not a local one; the key lives in its `.env` (gitignored, outside the document root `public/`). Serve it with `php -S 127.0.0.1:8080 -t examples/itp-api-basic-web-client/public` (PHP 8.2+). It is not part of the container image and nothing in `src/` depends on it. Do not call `curl_close()` in `api.php`: it is a no-op since PHP 8.0, and from 8.5 on its deprecation notice lands in the JSON response wherever `display_errors` is on, which breaks the page.

**Results on disk**: `APISpecification(results_root=...)` makes every interaction with persistence enabled record itself in `<results_root>/results/<timestamp>_<session prefix>/`. The folder and `interaction.json` (agents, their models and state spaces, context, number of turns, starting role) are written at creation, each ITP message file as it arrives (`Communication.save_message`), and `interaction.json` again at start and at the end with status, end reason and final turn. Ending early through `/end` therefore leaves everything up to then; with persistence off nothing is written. `run_model_api.py` passes the repo root; without `results_root` nothing is written. The folder name is returned as `resultsFolder` in `/results`.

**Ports** — no runner hard-codes one. `src/utils/ports.py` owns the policy: `ITP_API_PORT` / `ITP_UI_PORT` are obeyed exactly and fail loudly if taken; without them the first free port in 8001-8010 (API), 5173-5182 (mock client) or 8050-8059 (LASSI dashboard, `ITP_VISUALIZATION_PORT`) is used, so a leftover process or an unrelated service never forces you to evict it. The API's CORS list covers the whole UI range for that reason. Clients find the API through `discover_api_base_url`: `ITP_API_BASE_URL`, then `ITP_API_PORT`, then the `.itp-api-url` note a running API leaves at the repo root (verified before it is believed, so a stale one is harmless), then a probe of the candidate range for a live `/api/v1/models`. The note is removed on application shutdown, not in a `finally` around `uvicorn.run` — uvicorn re-raises the signal it caught, so control never returns there. `run_model_api` binds `0.0.0.0` (all interfaces) so the container can be reached from outside. On a laptop this makes the API reachable from the local network too. The printed URL and the `.itp-api-url` note still name `127.0.0.1` (`make_client_base_url`), because browsers have started to block requests to `0.0.0.0` and the note ends up in the mock client's base URL field. "Free" means binding succeeds **and** nothing answers a connection on `127.0.0.1` or `::1`: with `SO_REUSEADDR`, macOS lets a wildcard and a loopback bind of one port coexist, so a bind test alone misses a listener on the other address. Discovery asks `is_port_listening`, not `is_port_free`, for the same reason. `tests/test_ports.py` holds the mixed-address cases.

**Container**: `Dockerfile` builds the API image in two stages on `python:3.13-slim` and runs `python -m src.run_model_api` as an unprivileged `appuser` (uid 1000), exposing 8001. The image holds `src/`, `schema/` and `configs/` only; `.dockerignore` keeps out `tests/`, `.venv/` and `.git/`, and `ui/` is not copied because the mock client is not part of the deployment. `/app` itself stays owned by root, so from the Dockerfile alone `appuser` could not create `results/` or write the URL note, and both failures would be swallowed. The deployed API does record (2026-10-13: `/results` returned a `resultsFolder` for a persisted session, which is only set once the folder exists), so the deployment provides a writable `/app/results`; how is not visible from this repo. A local `podman run` needs the volume shown under *Setup & run*. `.gitlab-ci.yml` builds a multi-arch image (amd64 and arm64) with buildah and pushes it as `itp-api` to the Harbor registry named by the `REGISTRY_*` CI variables, tagged with the git tag or short SHA and with `latest`. The job only runs when started by hand from the GitLab web UI; it does nothing on GitHub, where this checkout's remotes point. On GitLab, `cvmls/itp/itp-api` mirrors this repository from GitHub and runs that job; `cvmls/itp/itp-deployment` (Pascal's) deploys `harbor.uni-muenster.de/itp/itp-api:latest` to `https://itp-api.uni-muenster.de`, also by hand. A merge to `main` is live only after both; check the live `/docs/openapi.json` before telling a client a feature is there (since 2026-11-01 it runs `main` with PR #4: optional `turn`, action `cursor`, `parameterSpace`). The release steps are in `docs/deployment.md` under *Releasing a new API version*. PerTRAIN's `ITPGenerator` needs the 2026-10-27 `main` for actions, and the `parameterSpace` release for its parameter fields; an older server accepts a `configuration` and ignores it. The interactive OpenAPI page is at `/docs` and the schema at `/docs/openapi.json` (moved from FastAPI's default `/openapi.json`). `.gitattributes` normalizes line endings (`* text=auto`).

Other modules: `src/interactioncontext/`, `src/utils/utilfuncs.py` (timecode + conversion helpers, `load_config`, `make_iso_timestamp`). `src/deprecated/` is dead code, including the previous `/sessions` API. `schema/` holds JSON Schemas and example ITP messages; `configs/` holds the context and formal model parameter configs.

## Setup & run

Run everything from the **repo root as modules** (imports are `from src....`, and there are no `__init__.py` files, so `python src/foo.py` fails — use `-m`).

```bash
source .venv/bin/activate
python -m pip install -r requirements.txt

# local interaction between two dummy models
python -m src.run_local_interaction

# API-based interaction (two terminals)
python -m src.run_model_api        # serves the catalogue at http://127.0.0.1:8001, or the next free port
python -m src.run_API_interaction  # runs model-model, human-model, human-human

# LASSI state distribution dashboard at http://127.0.0.1:8050, or the next free port
python -m src.run_lassi_visualization

# browser mock client of the API, in a third terminal (open http://127.0.0.1:5173)
python -m src.run_mock_ui

# self-contained HTML report of a recorded interaction (results/<folder>/interaction_report.html)
python -m src.run_interaction_report --latest
python -m src.run_interaction_report results/<folder> --text dialogue.csv --label A="IPC model"

# conformance test of LASSIFormalModel against the lassi_simulations vectors
python -m pytest tests

# the API as a container (podman or docker), with a volume so results survive
podman build -t itp-api .
podman run -p 8001:8001 -v "$PWD/results:/app/results" itp-api
```

## Conventions

- Python 3.13, `from __future__ import annotations`, type hints throughout.
- Pydantic for validation; FastAPI + uvicorn for the API; `jsonschema` for state vector validation; Dash + plotly for visualization.
- Docstrings use `Args:` / `Returns:` sections — match this style.
- No linter is configured yet. `tests/test_api_interactions.py` covers two different models in one interaction, per-agent model reporting, ending early with the record kept, the record written at creation, the restart answer, actions without a turn, the action cursor, and recovery through a repeated `clientRequestId`, all in-process. `tests/test_model_parameters.py` covers the published LASSI space, defaults, seeded and unseeded draws, explicit values over a draw, the refusals, and parameters plus `clientRequestId` in the record. `tests/test_interaction_report.py` covers the record pairing, the dialogue join and its refusals, the plane orientation, and the written page. `tests/test_ports.py` covers the port policy and API discovery, on OS-assigned ports so a running API cannot affect it. `tests/test_lassi_formal_model.py` runs the conformance vectors of `lassi_simulations` (`tests/data/lassi_test_vectors.json`, a copy of `handoff/test_vectors.json` there) against `LASSIFormalModel`. Run them with `python -m pytest tests` from the repo root. The three copies of that model — `lassi_simulations`, here, and the PerTRAIN production repo — are separate implementations feeding the same published claims, nothing detects drift between them, and these vectors are the only mitigation. When the model changes there, the file is regenerated and copied over this one; a mismatch is a release blocker, not a rounding question.
